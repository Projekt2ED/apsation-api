## 1. 目标

第一版目标不是自研一个中转平台，而是在成熟底层能力之上，快速做出一个可交付的 ToB 品牌站，满足：

- 客户可登录
- 客户可拿到 Key
- 客户可在 Playground 验证主流模型能力
- 客户可查看日志和异步任务
- 运营可手工开通客户和模型权限

## 2. 总体原则

- 底层中转能力优先复用
- 前台品牌站和 Playground 可以自定义
- 第一版不做在线充值
- 第一版不做复杂钱包和结算
- 第一版优先打通演示链路和接入链路

## 3. 推荐架构

建议采用 4 层结构：

1. 品牌站前端
2. 控制台前端
3. 轻量 BFF / 站点服务层
4. 底层中转平台

架构关系：

`Browser -> 品牌站/控制台 -> BFF -> 中转平台 API -> 各模型渠道`

## 4. 各层职责

### 4.1 品牌站前端

职责：

- 首页展示
- 模型目录展示
- 文档入口
- 公告与 FAQ
- 登录入口

建议：

- 做成 SEO 和首屏体验更好的站
- 与控制台风格统一，但路由层面分清

### 4.2 控制台前端

职责：

- 工作台
- Playground
- 令牌管理
- 调用日志
- 异步任务
- 账号设置

要求：

- 请求交互稳定
- 流式输出体验可用
- 对图片、音频、视频结果能直接展示

### 4.3 BFF / 站点服务层

职责：

- 聚合和清洗底层平台接口
- 对外暴露统一的前端友好接口
- 做权限控制和字段收敛
- 隐藏底层平台实现细节
- 承接 Playground 代码示例生成

说明：

如果底层平台前端接口已经足够干净，第一版可以薄 BFF；如果底层接口杂乱，BFF 就必须做。

### 4.4 底层中转平台

职责：

- 账号体系
- Key 管理
- 模型接入
- 调用转发
- 日志记录
- 异步任务记录
- 基础额度控制

建议：

- 优先评估 `New API / one-api` 一类成熟方案
- 第一版不要改动核心网关逻辑，先在前台做品牌和产品层封装

## 5. 为什么需要 BFF

即使底层平台已可用，也建议保留一层轻量 BFF，原因：

- 方便把底层字段改造成品牌站自己的结构
- 避免前端直接依赖底层平台全部接口细节
- 后续替换底层实现时，前端不用整体重写
- 便于加自定义模块，例如 Playground 预设和客户级模型目录

## 6. 第一版建议支持的能力范围

### 6.1 文本类

- `/v1/chat/completions`
- `/v1/responses`
- `/v1/messages`

### 6.2 向量与检索类

- `/v1/embeddings`
- `/v1/rerank`

### 6.3 图片类

- `/v1/images/generations`
- `/v1/images/edits`
- `/v1/images/variations`

### 6.4 音频类

- `/v1/audio/speech`
- `/v1/audio/transcriptions`
- `/v1/audio/translations`

### 6.5 视频与异步任务类

- 统一的视频生成入口
- 任务提交结果展示
- 任务轮询与结果查看

说明：

第一版要覆盖“主流能力形态”，但不建议在 UI 上为每一个非常规私有接口都单独做一个页面。

## 7. Playground 设计要求

### 7.1 目标

Playground 不是摆设，它要承担两个任务：

- 给客户快速验证“这个模型能不能用”
- 给售前和售后快速定位“是接口问题还是参数问题”

### 7.2 页面结构

建议分为三栏：

- 左侧：协议/模式切换与模型选择
- 中间：请求参数区
- 右侧：结果展示区

### 7.3 至少支持的模式

- Chat
- Responses
- Messages
- Images
- Audio
- Video / Tasks

### 7.4 必须支持的功能

- 流式结果展示
- JSON 请求体预览
- JSON 返回体查看
- 一键复制 `curl`
- 一键复制 `Python`
- 一键复制 `JavaScript`
- 图片预览
- 音频播放器
- 视频任务状态刷新

### 7.5 建议支持的增强功能

- Playground 请求模板
- 最近一次请求恢复
- 错误字段高亮
- 基于当前请求生成文档示例

## 8. 数据模型建议

第一版至少需要这些核心对象：

- `organization`
  表示客户组织
- `user`
  表示登录用户
- `api_token`
  表示 API Key
- `model_registry`
  表示模型元数据
- `organization_model_access`
  表示客户可用模型范围
- `quota_ledger`
  表示手工加额和额度调整记录
- `request_log`
  表示调用日志
- `async_task`
  表示异步任务记录
- `playground_preset`
  表示操场预设
- `announcement`
  表示公告
- `faq_item`
  表示 FAQ

## 9. 前端技术建议

如果没有现成代码包袱，建议：

- 品牌站与控制台统一用 `TypeScript`
- 前端框架优先选支持 SSR/路由一体化的方案
- 组件层优先做一套自有设计系统，而不是直接照搬底层平台样式

推荐思路：

- 官网和控制台统一一个 Web 应用
- 公开页面走 SSR 或静态输出优先
- 控制台页面走客户端交互优先

原因：

- 文档、模型页、首页更适合 SEO 和首屏加载
- Playground、日志页、任务页更适合强交互

## 10. 接口分层建议

### 10.1 面向前端的站点接口

建议由 BFF 暴露：

- `/site/models`
- `/site/announcements`
- `/site/faq`
- `/console/me`
- `/console/tokens`
- `/console/logs`
- `/console/tasks`
- `/console/playground/presets`

### 10.2 Playground 调用方式

建议不要让 Playground 直接拼接任意底层接口地址。

建议方式：

- 前端提交统一结构给 BFF
- BFF 根据模式和模型映射到真实协议
- BFF 代发请求到中转平台
- BFF 将结果流式透传回前端

好处：

- 便于审计
- 便于限流
- 便于生成标准代码示例
- 便于屏蔽底层差异

## 11. 权限与客户管理建议

第一版建议至少有 3 类权限：

- 访客
- 客户用户
- 运营管理员

客户维度至少要控制：

- 是否可登录
- 是否可创建 Key
- 可用模型范围
- 是否可用 Playground
- 基础额度状态

## 12. 部署建议

第一版建议分开部署：

- Web 站点
- BFF 服务
- 底层中转平台
- 数据库和缓存

反向代理层统一接入：

- `www.xxx.com` 对外官网
- `api.xxx.com` 对外 API 入口
- `console.xxx.com` 或同域 `/console` 对外控制台

如果希望简单，第一版也可以合并成一个主站域名加分路由，但 API 域名建议独立。

## 13. 日志与排障建议

第一版至少要保证：

- 每次 Playground 请求能定位到真实转发请求
- 每个异步任务能查状态
- 每次失败能看到错误原因
- 运营能按客户、模型、时间检索

这部分直接决定 ToB 售后是否能跑起来。

## 14. 风险点

### 14.1 模型种类过多

风险：

- Playground 容易做得很散
- 文档和模型页容易失控

处理：

- 先按能力类型聚合
- 再按协议分组
- 不按供应商接口逐个堆页面

### 14.2 底层平台字段不稳定

风险：

- 前端直接耦合后续难改

处理：

- 用 BFF 做字段收口

### 14.3 视频与异步任务体验差

风险：

- 客户会误以为平台不可用

处理：

- Playground 必须内置任务轮询和结果态展示

## 15. 实施顺序建议

### Phase 1

- 接通底层平台
- 确认模型目录接口
- 确认 Key、日志、任务接口

### Phase 2

- 做官网页面
- 做登录和控制台骨架
- 做模型页和文档页

### Phase 3

- 做 Playground
- 做日志和任务页
- 做 Key 管理页

### Phase 4

- 做运营配置能力
- 做 Playground 预设
- 做客户权限控制
