# 套壳 API 站 PRD（V0.2）

更新时间：2026-04-27  
状态：已确认方向，待进入信息架构与技术设计  
目的：明确 ToB 第一版产品边界、MVP 范围和落地顺序，再开始设计与开发。

## 1. 项目背景

我们计划做一个“套壳 API 站”，核心不是重新发明模型中转能力，而是基于成熟的 API 中转/聚合能力，做一个可品牌化、可交付、可运营、可支持企业客户接入的站点。

本轮 PRD 参考了 `https://api.bltcy.ai/` 的公开页面、公开接口和前端路由。观察时间为 2026-04-27。由于对方站点后续可能更新，本文只作为当前阶段的产品抽象，不作为永久事实来源。

## 2. 参考站拆解

### 2.1 参考站产品定位

`api.bltcy.ai` 不是单一落地页，而是一个完整的“营销站 + 用户控制台 + API 接入平台”。

从首页元信息、菜单配置和公开接口来看，它强调以下卖点：

- 多模型聚合：OpenAI、Claude、Gemini、Midjourney、Suno、Luma 等
- 协议兼容：支持 OpenAI、Anthropic 等常见格式
- 价格与稳定性：低价、并发、线路优化、风控兜底
- 自助接入：注册、令牌管理、文档、模型目录、日志和任务查询
- 运营能力：公告、FAQ、教程文档、模型排行、在线体验入口

### 2.2 参考站公开可见模块

公开菜单和路由里能确认这些模块：

- 首页
- 工作台
- 个人中心
- 钱包/充值
- 聊天体验
- 数据看板
- 绘图记录
- 操作日志
- 异步任务
- 令牌管理
- 教程文档
- API 文档
- 支持模型
- 模型排名

### 2.3 参考站公开能力特征

从公开接口、前端 bundle 和状态配置可确认：

- 支持的主协议接口包含 `/v1/chat/completions`、`/v1/responses`、`/v1/messages`、`/v1/embeddings`、`/v1/rerank`
- 支持图片接口：`/v1/images/generations`、`/v1/images/edits`、`/v1/images/variations`
- 支持语音接口：`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/audio/translations`
- 支持视频和异步任务类接口
- 支持注册、邮箱验证、GitHub OAuth、数据导出、OSS 上传、任务通知
- 提供模型文档、FAQ、公告、在线体验入口

### 2.4 对参考站的技术判断

基于响应头 `X-New-Api-Version`、公开配置里的 `docs.newapi.pro`、以及整体路由结构，推测它大概率基于 `New API / one-api` 这一类中转面板体系做了前台定制。

这是推断，不是对源码的直接确认。

## 3. 我们要做的产品定义

### 3.1 产品名称

暂定：`<你的品牌名> API`

### 3.2 产品定位

一个面向企业研发团队、SaaS 团队和集成方的“多模型 API 接入平台”，提供统一鉴权、统一文档、统一调用入口和可直接验证能力的 Playground，让客户能先验证，再集成，再放量。

### 3.3 核心价值

- 对客户：少折腾，多模型统一接入，先在 Playground 验证，再拿 Key 集成
- 对运营方：统一品牌、统一客户入口、统一模型目录、统一售后排障
- 对业务：先把站跑起来，先把模型调用和演示链路打通，再考虑更复杂的计费和运营系统

### 3.4 本轮已确认决策

- 业务方向：`ToB 优先`
- 第一版：`不做在线充值`
- 第一版：`必须有可用 Playground`
- 第一版：`对话、图片、音频、视频、向量/重排序、异步任务等主流能力一起覆盖`

说明：这里的“都一起做”指第一版覆盖主流能力形态，不等于一次性兼容每一家供应商的全部私有特殊接口。第一版仍以“主流协议 + 主流模型能力 + 可用演示链路”为准。

### 4.2 次级用户

## 5. 产品目标与非目标

### 5.1 第一阶段目标

- 7 天内完成产品结构与技术方案定义
- 2 到 4 周内上线可演示、可交付的 ToB MVP
- 客户可以完成登录、获得开通额度、进入 Playground、成功调用主流模型接口
- 运营可以管理客户、令牌、模型开关、公告和基础排障数据

### 5.2 非目标

- 第一阶段不追求自研模型调度内核
- 第一阶段不追求在线充值和复杂钱包系统
- 第一阶段不追求复杂分销体系
- 第一阶段不追求覆盖所有供应商的全部私有协议

## 6. 产品策略

### 6.1 推荐路线

优先走：

`成熟中转内核 + 自定义品牌前台 + 自定义控制台 + 可用 Playground`

不建议一开始就自研：

- 网关层
- 多渠道调度
- 配额计费引擎
- 风控与熔断系统
- 完整运维后台

### 6.2 原因

- 上线快，能先验证客户是否愿意接入
- 技术风险小
- 可以先把精力放在品牌、页面、文档、Playground、售前演示和售后排障
- 后续如果 ToB 客户稳定，再逐步替换底层能力

## 9. 核心用户流程

### 9.1 新客户首次接入

1. 进入首页了解支持能力和接入方式
2. 查看支持模型和协议
3. 联系商务或被手工开通账号
4. 登录控制台
5. 在 Playground 验证模型可用性
6. 创建 API Key
7. 复制示例代码接入业务系统
8. 在日志页核对调用结果和错误信息

### 9.2 老客户持续使用

1. 登录工作台
2. 查看公告、配额和开通能力
3. 在 Playground 调试新模型
4. 管理令牌
5. 查看日志/异步任务
6. 联系支持扩容或开通更多模型

### 9.3 售后排障

1. 客户在 FAQ 未解决后联系人工支持
2. 支持基于客户 ID、令牌、请求日志、任务 ID 定位问题
3. 通过公告、FAQ 或 Playground 示例回填共性问题

## 10. 功能需求明细

### 10.1 首页

首页需要完成三件事：

- 讲清楚支持什么能力
- 证明为什么可信
- 把客户导向文档、模型页和申请开通

首页建议模块：

- Hero 区：品牌、核心卖点、CTA
- 支持能力区：对话、图像、语音、视频、向量
- 协议兼容区
- 接入流程区
- 典型业务场景区
- 公告或最新动态
- FAQ 摘要
- 页脚合规说明

### 10.2 模型页

模型页需要支持：

- 按供应商筛选
- 按能力筛选：对话、图片、音频、视频、向量
- 展示模型名、接口格式、状态、备注
- 跳转到对应文档示例

### 10.3 接入/合作方式页

这一页需要讲清楚：

- 支持的协议范围
- 支持的能力范围
- 开通方式
- 额度和调用限制说明
- 同步/异步接口说明
- 支持与售后方式

### 10.4 令牌管理

令牌页至少支持：

- 创建 Key
- 自定义名称
- 查看状态
- 重置/删除
- 复制
- 设置备注

### 10.5 日志与任务

至少支持：

- 时间筛选
- 模型筛选
- 状态筛选
- 请求消耗展示
- 错误原因查看
- 异步任务进度查询

### 10.6 Playground

Playground 是第一版核心模块，至少要支持：

- Chat 模式
- Responses 模式
- Messages 模式
- Images 模式
- Audio 模式
- Video/Task 模式
- 流式响应展示
- 图片结果预览
- 音频结果播放
- 视频任务轮询和结果查看
- 一键复制代码示例

## 16. 当前建议的产品边界

如果现在的目标是“尽快上线一个像样、能演示、能交付给 ToB 客户的站”，建议第一版只做：

- 品牌官网
- 支持模型页
- 文档入口
- 登录
- 工作台
- Playground
- Key 管理
- 日志查询
- 异步任务查询
- 客户手工开通/手工加额

先不做：

- 在线充值
- 钱包
- 商城
- 发票
- 分销
- 多代理层级

这会让第一版足够像一个完整产品，但不会重到失控。
