# GPT-5.5 使用指南

## 简介

GPT-5.5 提升了复杂生产工作流的基准水平。它非常适合以下场景：编码、工具密集型智能体、基于知识库的助手、长上下文检索、从产品规格到执行计划的工作流，以及对执行质量和回复质量要求较高的面向客户的工作流。

要充分发挥 GPT-5.5 的能力，请把它当作一个**全新的模型系列来调优**，而不是 `gpt-5.2` 或 `gpt-5.4` 的直接替换品。迁移 时请从全新的基线开始，不要把旧模型的所有提示词原封照搬过来。先用最小的提示词保留产品契约，然后针对代表性用例调优推理强度、详细度、工具描述和输出格式。

GPT-5.5 支持 GPT-5.4 已有的全部 API 功能，包括：

- **提示缓存**（Prompt Caching）
- **工具**（Tools）
- **工具搜索**（Tool Search）
- **压缩**（Compaction）
- **阶段处理**（Phase handling）——用于手动回放 assistant 条目

## 新特性

- **更高效的推理**：GPT-5.5 用更少的推理 token 就能达到很强的效果，即使在相同的推理强度设置下也是如此。在复杂的、工具密集的或多步骤的工作流中特别有用，因为 token 节省会逐层累积。
- **以结果为导向的提示词带来更强的执行力**：GPT-5.5 更擅长从清晰的目标出发，保持约束条件，把产品意图转化为具体的下一步操作。请描述期望结果、成功标准、允许的副作用、证据规则和输出格式。除非精确路径很重要，否则避免逐步的过程指导。
- **更强大、更精准的工具使用**：GPT-5.5 在大型工具集、多步骤服务工作流和长时间运行的智能体任务中尤为出色。它在工具选择和参数使用上更加精确。
- **语气通常更流畅，但也更直接**：GPT-5.5 通常用更少的提示词支架就能产出更温暖、更可读的回答。

## 行为变化

### 1. 推理强度默认为 `medium`

GPT-5.5 默认使用 `medium`（中等）推理强度。将其视为质量、可靠性、延迟和成本的**推荐平衡起点**。

- 对于延迟敏感的工作流，如果仍涉及工具使用、规划、搜索或多步决策，先尝试 `low` 而不是 `none`。
- `none` 仅保留给不需要推理或多链工具调用的延迟关键任务，如轻量级语音对话、快速信息检索和分类。
- 只有当评估显示有可衡量的质量提升时，才提升到 `high` 或 `xhigh`。

**注意**：更高的推理强度并不自动等于更好的效果。如果任务包含矛盾的指令、弱停止标准或开放式工具访问，更高的强度可能导致过度思考、不必要的搜索或输出质量下降。只有在评估显示有可衡量的质量增益时才提高强度。

### 2. 图像输入默认保留更多视觉细节

GPT-5.5 更新了图像输入的默认处理方式，保留更多视觉细节以提升计算机操作（Computer Use）的表现。

- `auto` 或未设置时：现在等同于 `original` 行为，不缩放图像，上限为 10,240,000 像素或单边最大 6,000 像素。
- `high`：需显式指定，不缩放图像，上限为 2,500,000 像素或单边最大 2,048 像素。
- `low`：更激进地缩放超过 512 像素边长限制的图像，比之前的模型更注重上下文效率。

### 3. 指令跟随能力增强

GPT-5.5 以**字面且彻底**的方式理解提示词，因此当产品需要时，可以使用更具体、更具描述性的指令。对于长时间运行、工具密集或需要收集证据的工作流，请明确定义成功标准和停止规则。

### 4. 默认风格更简洁直接

GPT-5.5 默认倾向于高效、直接和以任务为导向。这对许多生产工作流很有用，但面向客户或对话式的场景可能需要显式地提供个性、温度、逻辑说明和格式指引。

- 使用 `text.verbosity` 来控制：`medium` 是默认值，`low` 通常是简洁回复的更好起点。

### 5. 编码工作流需要更强的编排

GPT-5.5 更适合需要规划、工具使用、代码库导航、验证和多步骤执行的复杂编码任务。对于编码智能体，请明确说明：复用策略、子智能体委派、测试期望、验收标准，以及何时继续执行 vs 何时请求帮助。

## 迁移快速入门

### API 和模型参数调整

1. 将模型标识改为 `gpt-5.5`。
2. 对于推理、工具调用或多轮对话场景，使用 **Responses API**。
3. 调整 `reasoning.effort`：
   - `low` — 高效推理
   - `medium` — 延迟/性能曲线的平衡点
   - `high` — 需要强推理的复杂智能体任务，延迟不太敏感
   - `xhigh` — 最难的异步智能体任务或测试模型智力上限的评估
4. 需要更简洁回复时，设置 `text.verbosity` 为 `low`。在 GPT-5.5 上，`low` 会比 GPT-5.4 的 `low` 产出更简洁的回复。
5. 对于工具密集或长时间运行的工作流，确保你的应用能正确处理 `phase`、前言（preambles）和 assistant 条目回放。
6. 在准确性、token 消耗和端到端延迟上对标其他模型进行基准测试。

### 提示词优化建议

1. **说明期望结果和成功标准**，而不是详细的步骤指引。
2. **减少或移除详细的逐步过程指导**。让 GPT-5.5 自行选择路径，除非产品严格要求某条特定路径。
3. **尽可能移除提示词中的输出格式定义**，改用结构化输出（Structured Outputs）来自动验证。
4. **优化提示词以利用缓存**：保持稳定内容在请求开头，动态的用户特定上下文放在末尾。
5. **移除当前日期**。模型已经知道当前 UTC 日期，无需在系统指令中添加。只有当应用需要业务特定的时区、政策生效日期、用户本地日期等非 UTC 参考点时，才需要显式添加日期/时区上下文。

## 推理模型使用要点

以下建议适用于 GPT-5 系列模型。如果你是从早期 GPT-5 模型、GPT-4.1 或 o3 等推理模型迁移过来，值得重新审视这些功能。GPT-5.5 延续了早期模型的许多能力，但以下要点仍然值得回顾：

### Responses API

GPT-5.5 在 Responses API 中表现最佳。使用 `previous_response_id` 进行多轮状态管理。对于无状态或零数据保留流程，每轮传回相关的输出条目。

### 推理强度（reasoning.effort）

选择 `low` / `medium` / `high` / `xhigh`。默认为 `medium`，但很多工作负载用 `low` 就表现很好。`none` 保留给延迟比智能更重要的场景。

### 详细度（verbosity）

使用 `text.verbosity` 控制输出长度。将最终回答长度和推理质量分开看待；如有需要可指定字数预算、段落数、表格宽度或纯 JSON 输出。

### 结构化输出（Structured Outputs）

**避免在提示词中描述期望的输出格式**。使用结构化输出功能来自动验证并提高准确性。

### 提示缓存（Prompt Caching）

- 对符合条件的长提示词自动生效，可降低延迟和输入 token 成本。
- 最大化缓存命中：保持稳定内容在请求开头，动态上下文放在末尾。
- 对重复流量使用公共前缀时，一致使用 `prompt_cache_key` 并追踪 `usage.prompt_tokens_details.cached_tokens`。

### 工具调用（Tool Calling）

GPT-5.5 支持与 GPT-5.4 相同的工具调用模式，包括函数工具和工具密集型智能体工作流。**将大部分工具特定的指引放在工具描述中**：工具做什么、何时使用、所需输入、副作用、重试安全性和常见错误模式。仅当指引适用于跨工具或实质性改变智能体运行策略时，才添加到系统指令中。

### 托管工具和工具搜索

优先使用托管工具（web search、file search、code interpreter、image generation、computer use），它们减少自定义编排负担。只有当需要调用自己的系统、执行特定领域的副作用或暴露内部业务工作流时，才使用自定义函数工具。对于大型工具目录，考虑使用工具搜索来延迟加载工具定义。

### 工具前言（Tool Preambles）

前言可以改善聊天体验——用户在模型生成最终回复前先看到有用的初始状态更新。它们也让工具使用更容易理解：模型可以先声明即将检查或做什么，然后从该 assistant 状态继续。

### 阶段处理（phase handling）

如果你的应用通过每轮传回输出条目来手动管理 Responses 状态（而非使用 `previous_response_id`），请保留返回的 assistant 输出条目上的 `phase` 参数并原样传回。在使用推理强度、前言或重复工具调用时尤其重要。

### 压缩（Compaction）

对于长时间运行的智能体，有意识地使用压缩功能。保留：已完成的操作、活跃假设、ID、工具结果、未解决的阻塞点，以及下一个具体目标。

### Agents SDK

对于新的智能体系统，使用最新的 Agents SDK 模式进行工具编排、追踪、交接和状态管理，而不是从零重建编排逻辑。
